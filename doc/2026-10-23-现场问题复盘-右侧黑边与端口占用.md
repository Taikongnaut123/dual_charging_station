# 现场问题复盘：右侧黑边 & 无法绑定 UDP 8891

> 日期：2026-10-23
> 目标机：`EPC-TL3588-BU`（RK3588），内核 `6.1.141-rt36 PREEMPT_RT`，Qt `5.15.11`
> 显示器：8 寸 1024×768（4:3）HDMI，驱动板 RTD2513BR
> 现象由现场反馈，通过 SSH（`192.168.21.24`）远程定位并验证

两个问题看起来都像是"界面写错了"，实际根因都在系统层：一个在 DRM/fbdev，
一个在进程管理。下面按「现象 → 排查 → 根因 → 修复 → 验证」记录。

---

## 问题一：界面右侧有一条黑边

### 现象

界面内容只占左边一大块，右边固定一条竖直黑边，程序本身不报任何错误。

### 排查过程

**1）先看 framebuffer 到底是什么尺寸**

```bash
$ cat /sys/class/graphics/fb0/virtual_size
1024,1280

$ fbset -i -fb /dev/fb0

mode "800x768"
    geometry 800 768 1024 1280 32      # xres yres xres_virtual yres_virtual
    timings 0 0 0 0 0 0 0
    accel true
    rgba 8/16,8/8,8/0,0/0
endmode

Frame buffer device information:
    Name        : rockchipdrmfb
    Size        : 5242880
    LineLength  : 4096                 # 每行 4096 字节 = 1024 像素
```

关键的不一致出现了：**缓冲区每行实际有 1024 像素，内核却只说可见宽度是 800。**

**2）再看有哪几路输出在工作**

```bash
$ for d in /sys/class/drm/card*-*; do
      printf "%-16s %-14s %s\n" "$(basename $d)" "$(cat $d/status)" "$(cat $d/enabled)"
  done
card0-DP-1          disconnected   disabled
card0-DSI-1         connected      enabled      # 板载 MIPI 屏，800x1280（竖屏）
card0-HDMI-A-1      connected      enabled      # 8 寸屏，1024x768
card0-Writeback-1   unknown        disabled
card0-eDP-1         disconnected   disabled
```

**3）用 Rockchip 的 debugfs 看真实的扫描时序**

```bash
$ sed -n '1,40p' /sys/kernel/debug/dri/0/summary
Video Port0: ACTIVE
    Connector:HDMI-A-1  Encoder: TMDS-227
    Display mode: 1024x768p60                        # HDMI 本身是对的
    Esmart0-win0: ACTIVE
        src: pos[0, 0] rect[1024 x 768]
        dst: pos[0, 0] rect[1024 x 768]
        buf[0]: addr: 0x00000000edeb8000 pitch: 4096 offset: 0

Video Port3: ACTIVE
    Connector:DSI-1     Encoder: DSI-252
    Display mode: 800x1280p56
    Esmart3-win0: ACTIVE
        src: pos[0, 0] rect[800 x 1280]
        dst: pos[0, 0] rect[800 x 1280]
        buf[0]: addr: 0x00000000edeb8000 pitch: 4096 offset: 0
                                    ^^^^^^^^^^^^^^^^^^ 同一个地址！
```

**4）量一下实际画面**

把 `/dev/fb0` 原样导出，按 `1024×1280 / pitch 4096 / BGRA` 还原成图，统计每列平均亮度：

```
最右侧非黑列 x = 790
最下方非黑行 y = 757
```

即内容正好是 **800×768**，和 `fbset` 报的 `xres/yres` 完全吻合。

### 根因

RK3588 的 DRM fbdev 只创建**一块** `/dev/fb0`，被所有输出共用，尺寸取各路输出的**并集**：

| 来源 | 宽 | 高 |
|---|---|---|
| HDMI-A-1 | 1024 | **768** |
| DSI-1 | **800** | 1280 |
| **并集（xres_virtual × yres_virtual）** | **1024** | **1280** |

而 `fb_var_screeninfo` 里报给用户的"可见尺寸"被拼成了一个**不存在的模式**：
`xres=800`（DSI 的宽）× `yres=768`（HDMI 的高）。

Qt 的 linuxfb 平台插件启动时读 `FBIOGET_VSCREENINFO`，只认 `xres`/`yres`：

- 认为屏幕 = 800×768
- `showFullScreen()` 后窗口 = 800×768
- 每行按 `fixinfo.line_length`（4096 字节 = 1024 像素）跳，但只写前 800 像素
- **每行剩下 224 像素没人写 → 永远保持 fb 初始值（黑）**

这就是"右侧一条黑边"的完整链路。注意它不是"界面没适配"，界面是忠实地铺满了它
看到的 800×768。

### 修复

在 `main.cpp` 中新增 `fixFbdevGeometryIfUnioned()`，在 **Qt 加载平台插件之前**
（即 `QApplication` 构造之前）把 `xres` 纠正为真实行宽。

触发条件（三个都满足才动手）：

1. 平台是 `linuxfb`（走 X 时由 X 自己处理，不碰）
2. `/sys/class/drm/card*-*` 中 `status=connected` 且 `enabled=enabled` 的输出 **≥ 2 路**
3. `xres_virtual > xres` 且 `line_length * 8 / bits_per_pixel == xres_virtual`

第 2、3 条是安全阀：

- **单屏板子不会触发** —— fbdev 尺寸本来就是对的
- 有些单屏板子用 `xres_virtual` 做 panning，条件 2 会把它排除，避免把内容推到画面外
- 确实需要关闭时，设环境变量 `DCS_NO_FB_FIX=1`

同一处还加了屏幕方向/宽高比自检：当屏幕宽高比与设计稿 `1360×800`（1.70）差得太多
（或干脆是竖屏）时，直接在终端告警，提示去改输出模式，避免把"输出模式不对"误判成
"界面没适配"。

修复后启动日志：

```
[显示] 没有可用的 X（DISPLAY=），改用 framebuffer（linuxfb）
[显示] 多路输出共用一块 framebuffer：内核报可见宽度 800，实际行宽 1024，已修正（否则右侧会留一条黑边）
```

### 验证

**故意把故障复原再启动**，确认程序自己能纠回来（而不是靠手工 `fbset`）：

```bash
$ fbset -fb /dev/fb0 -xres 800 -yres 768      # 复原成故障状态
$ fbset -i -fb /dev/fb0 | head -3
mode "800x768"
    geometry 800 768 1024 1280 32

$ ./run_ui.sh -f                               # 启动新版本
$ fbset -i -fb /dev/fb0 | head -3
mode "1024x768"
    geometry 1024 768 1024 1280 32             # 已被程序自动修正
```

导出画面复核：

```
最右侧非黑列 x = 1011     （1024 减去卡片外边距，正常）
最下方非黑行 y = 756
```

### 更彻底的做法（备选，未采用）

如果这块板子**根本不用板载 MIPI 屏**，可以在内核参数里把它关掉，让 fbdev 直接按
HDMI 的尺寸创建，从源头消除"并集尺寸"：

```
video=DSI-1:d
```

**未采用的原因**：该板启动参数来自 U-Boot / boot 分区（`/dev/mmcblk0p3`，无
`extlinux.conf`、无 `uEnv.txt`、无 `fw_setenv`），修改需要重打包 boot 镜像，
风险与收益不成比例。程序内修正已经解决问题，且不影响任何其它子系统。

若将来要改，参考：

```bash
cat /proc/cmdline                       # 现有参数
lsblk -o NAME,SIZE,PARTLABEL            # boot = mmcblk0p3
modetest -c                             # 确认连接器名字（HDMI-A-1 / DSI-1）
```

## 问题二：启动报 `无法绑定 UDP 8891，已退回环回仿真模式`

### 现象

在控制台执行 `./run_ui.sh`，输出：

```
[显示] 没有可用的 X（DISPLAY=:0），改用 framebuffer（linuxfb）
无法绑定 UDP 8891，已退回环回仿真模式
```

（第一行是正常的自动回退，不是错误。）

### 排查过程

```bash
$ ss -lunp | grep 8891
UNCONN 0 0 0.0.0.0:8891 0.0.0.0:* users:(("dual_charging_s",pid=4849,fd=15))

$ pgrep -af 'bin/dual_charging_station'
4849 /home/chric/software/dual_charging_station-linux-arm64/bin/dual_charging_station -f
4995 /home/chric/software/dual_charging_station-linux-arm64/bin/dual_charging_station
```

**两个界面实例同时在跑**：`4849` 先绑定并占住了 8891，`4995`（后启动的）绑不上。

### 根因

UDP 8891 是界面接收 `mdc_bridge` 数据的端口（桥只发不收，界面只收不回）。这个端口
同一时刻只能被一个进程绑定。

旧代码在绑定失败时**静默降级**：

```cpp
if (!window.startBridge(statPort))
{
    // 端口被占用等情况：退回环回模式，至少让界面可用
    qWarning("无法绑定 UDP %u，已退回环回仿真模式", unsigned(statPort));
    window.setLoopbackEnabled(true);     // ← 问题所在
}
```

降级到"环回模式"后，界面按内置仿真器生成的假数据渲染：

- 界面照常动，SOC、电压、电流、累计电量全都在跳
- 链路显示"在线"、帧率 2Hz、丢帧 0
- **看起来一切正常，但没有一条是真实设备数据**

这比"起不来"危险得多——现场排障时会拿着假数据去对真设备，越查越偏。而且两个实例
同时往同一块 framebuffer 上画，画面会互相覆盖。

### 修复

**改为失败即退出**（退出码 2），并把排查指引直接打在终端上：

```
[链路] 无法绑定 UDP 8891 —— 通常说明已经有一个界面实例在运行。
       同一个屏幕上只应有一个实例，先确认并关掉旧的：
           pgrep -af bin/dual_charging_station
           pkill -f bin/dual_charging_station
       如果只是想看仿真数据，请显式加 --loopback。
```

要点：

- 想看仿真数据必须**显式**加 `--loopback`，不能靠"碰巧绑不上"进入
- 退出码用 2，方便脚本和 systemd 区分"正常退出"与"配置冲突"
- systemd unit 增加 `RestartPreventExitStatus=2`，避免端口冲突时每 3 秒重拉一次，
  把真正的报错冲出屏幕
- 冒烟测试 `tools/ci_smoke_test.sh` 的"假通过防护"同步更新注释

### 验证

```bash
# 先用一个进程占住 8893
$ python3 -c "import socket,time;s=socket.socket(socket.AF_INET,socket.SOCK_DGRAM);s.bind(('0.0.0.0',8893));time.sleep(25)" &
# 再启动界面
$ ./build/dual_charging_station --stat-port 8893; echo "退出码=$?"
[链路] 无法绑定 UDP 8893 —— 通常说明已经有一个界面实例在运行。
       ...
退出码=2
```

## 衍生发现：两个 `mdc_bridge` 导致"帧率翻倍 + 丢帧统计失真"

修完上面两个问题后，界面上仍然出现 `帧率 4 Hz`（设备实测 2Hz）和 `丢帧 5790`。

```bash
$ pgrep -af 'bin/mdc_bridge'
5188 .../bin/mdc_bridge
5230 .../bin/mdc_bridge

$ ros2 topic info /mdc_data
Publisher count: 1        # mdc_node 只有一个
Subscription count: 2     # 桥起了两个
```

两个桥各自订阅同一个话题、各自往 8891 发：

- 界面收到两路独立的帧流 → 帧率翻倍（4Hz）
- 两边的 `seq` 各算各的 → 界面按序号差算丢帧 → 累计出 5790 的虚假丢帧

清掉多余实例、重启界面后恢复：

```
[统计] 帧=20 速率=2Hz 丢帧=0 链路=在线 模式=待机 状态=空闲
```

**教训与问题二是同一类**：手动起进程容易产生重复实例，而重复实例的后果往往不是
"报错"，而是"数据静默变样"。

## 结论与建议

### 两个问题的共同点

| | 问题一（黑边） | 问题二（端口占用） |
|---|---|---|
| 表面现象 | 界面没铺满 | 界面正常但数据是假的 |
| 真实原因 | 系统层尺寸信息错误 | 进程重复 |
| 共同特征 | **都不报错，都"看起来能用"** | |

真正的技术债不在功能，而在**失败得不够响**。所以两个修复都遵循同一原则：

> 能在程序里纠正的就纠正（黑边），
> 纠正不了的就明确失败（端口冲突），**绝不允许静默降级**。

### 部署建议

1. **用 systemd 服务，不要手动起进程**

   ```bash
   cd /home/chric/software/dual_charging_station-linux-arm64
   sudo ./install_service.sh
   ```

   天然单实例、开机自启、崩溃自动拉起，并且已配置 `RestartPreventExitStatus=2`。

2. **排查顺序（现场照这个走）**

   ```bash
   # 1. 有几个实例？应当各一个
   pgrep -af 'bin/dual_charging_station'
   pgrep -af 'bin/mdc_bridge'

   # 2. framebuffer 尺寸对不对？
   fbset -i -fb /dev/fb0
   #    期望 geometry 的前两个数 = 面板分辨率（1024 768）

   # 3. 几路输出在工作？
   for d in /sys/class/drm/card*-*; do
       printf "%-16s %-14s %s\n" "$(basename $d)" "$(cat $d/status)" "$(cat $d/enabled)"
   done

   # 4. 真实扫描时序（Rockchip 专用）
   sed -n '1,40p' /sys/kernel/debug/dri/0/summary

   # 5. 界面到底收到真数据没有
   ./run_ui.sh -f --verbose
   #    看 "[统计] 帧=.. 速率=2Hz 丢帧=0 链路=在线"
   ```

3. **看到 `丢帧` 不为 0 或帧率不是 2Hz，先查重复桥**，不要怀疑协议。

### 已知遗留

- `mdc_bridge` **还没有单实例保护**。重复启动时不会报错，只会让数据变成双份、
  丢帧统计失真。可考虑加 `flock` 单实例锁（或用 systemd 托管，天然单实例）。
- 板载 DSI 屏仍在输出中（`800x1280`），只是不接屏。它目前是 fbdev 尺寸被撑大的
  唯一原因；如果将来这块屏彻底不用，可考虑在内核参数里 `video=DSI-1:d` 关掉。
